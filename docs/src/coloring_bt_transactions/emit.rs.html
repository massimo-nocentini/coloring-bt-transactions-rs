1//! # Formatting lines on more than one thread
2//!
3//! Turning a color into a line is the most expensive thing a text run does, and
4//! by a long way.  Measured over the first 150,000 records of
5//! `cargo run --release --example records -- --window 4000` — colors of some
6//! three thousand blocks by the end of it — with the fold and the parse held
7//! constant by comparing against `--sum`, which walks exactly the same terms
8//! and prints one number instead of all of them:
9//!
10//! ```text
11//!     --sets --fold /dev/null    2.43s      parse and fold, no lines
12//!     --sets                     4.70s      + 2.3 GB of terms
13//!     --weighted --sum           3.37s      parse and weighted fold
14//!     --weighted                50.18s      + 9.9 GB of terms
15//! ```
16//!
17//! Every number in this file names that corpus; `examples/records.rs` is what
18//! makes them checkable rather than merely stated.
19//!
20//! So formatting is 47% of an unweighted text run and 94% of a weighted one.
21//! The gap is [`crate::push_f64`]: the shortest round-tripping decimal costs
22//! about 133ns a term against 15ns for the integer path, and a weighted color
23//! spends one on every block it names.
24//!
25//! It is also the one part of the driver that is embarrassingly parallel.  A
26//! line is a pure function of `(tx_id, color)` — nothing about it looks at the
27//! store, at the records still to come, or at the line before it.
28//!
29//! ## What crosses the thread boundary
30//!
31//! A copy of the terms, not a handle on the color.
32//!
33//! Sharing the color itself is the obvious move and it is the wrong one here.
34//! It would mean `Rc` becoming `Arc` in both set backends, atomics on a
35//! refcount the fold thread touches several times a record, and — the real
36//! cost — an ownership question the stores currently answer exactly:
37//! [`crate::store::ColorStore::release`] decides whether an allocation is gone
38//! by asking whether it holds the last handle, and that question has no
39//! race-free answer once a second thread can hold one too.
40//!
41//! Copying sidesteps all of it.  A term is 12 bytes and a formatted term is
42//! about 22, so the copy is a memcpy against a decimal conversion: roughly 1ns
43//! a term against 133.  The stores keep their `Rc`, keep their layouts, and do
44//! not learn that threads exist; [`crate::poly`]'s arena, which could not have
45//! been shared at all, gets the same speedup as the others.
46//!
47//! ## Order, and why it costs nothing
48//!
49//! Record `i` goes to worker `i % threads` and the writer collects from worker
50//! `i % threads`, so the lines are written in the order they were dispatched
51//! without a sequence number, a reorder buffer, or a sort.  The output is
52//! byte-identical to the serial path — which matters beyond tidiness, since
53//! diffing `--rings` against `--sets` is how this crate checks one backend
54//! against the other, and a threaded run has to stay usable for that.
55//! `parallel_output_is_byte_identical` at the bottom of this file is the test.
56//!
57//! ## Closing it is not optional
58//!
59//! [`Pool::finish`] drains the pipeline and reports what the writer made of it,
60//! and `run` calls it — but only on the path that reaches the end of the
61//! records.  Every early return skips it, and a detached writer thread takes
62//! its buffer to the grave with it.  So the closing is in [`Drop`] as well,
63//! where the language runs it; `finish` is then the way to get at the *error*,
64//! not the way to make the output happen.  See the `impl Drop` below for what
65//! this used to cost.
66//!
67//! ## What bounds the memory
68//!
69//! Every channel into the pipeline is bounded, so a fold thread that outruns
70//! the formatters blocks instead of queueing.  The two channels *backwards* —
71//! the ones that hand a line buffer back to the worker that filled it and a
72//! snapshot back to the fold thread — are best-effort `try_send`: dropping a
73//! recycled buffer costs an allocation, where blocking on one would close a
74//! cycle in the wait graph and deadlock.  Nothing waits on recycling.
75

84/// How many batches may be in flight per worker.
85///
86/// Deep enough that a worker delayed on one long color does not stall the
87/// dispatcher, shallow enough that the pipeline holds a bounded and small
88/// multiple of a batch rather than an unbounded backlog of them.
89const DEPTH: usize = 4;
90
91/// Records a batch carries, and terms it carries, whichever it reaches first.
92///
93/// A batch rather than a record at a time because the channel costs the same
94/// whatever it carries, and what it carries varies by four orders of magnitude:
95/// a color of one block is a ten-byte line, and one of three thousand is fifty
96/// kilobytes.  Dispatching per record made a threaded run *slower than serial*
97/// on records whose colors stay small -- a microsecond of channel to hand over
98/// a line worth a hundred nanoseconds of work.
99///
100/// Over `--example records -- --window 0`, a million records whose every color
101/// is one block, where serial is 0.58s:
102///
103/// ```text
104///                     per record   batched
105///     --threads 1          1.59s     0.43s
106///     --threads 2          0.89s     0.43s
107///     --threads 4          1.19s     0.43s
108///     --threads 8          1.36s     0.43s
109/// ```
110///
111/// So both bounds, and neither alone.  [`LINES`] is what batches the small
112/// colors, where the record count is the cost; [`TERMS`] is what stops a batch
113/// of large ones from holding megabytes of formatted output per worker, where
114/// the byte count is.  A color of three thousand blocks fills a batch on its
115/// own, which is the right answer -- there the channel was never the problem.
116const LINES: usize = 256;
117const TERMS: usize = 8192;
118
119/// What follows the transaction id and the tab on a line.
120///
121/// One definition of it, driven either straight off the store on the fold
122/// thread or off a [`Snapshot`] on a worker, so the serial and threaded paths
123/// cannot drift into writing different bytes.
124pub struct Body<'a> {
125    line: &'a mut Vec<u8>,
126    form: Line,
127    weighted: bool,
128    /// Whether a term has been written, which is what puts the comma *between*
129    /// terms rather than after each of them.  `for_each_term` does not say
130    /// which term is last, so it is this rather than a truncation at the end.
131    written: bool,
132    sum: f64,
133}
134
135impl<'a> Body<'a> {
136    pub fn new(line: &'a mut Vec<u8>, form: Line, weighted: bool) -> Self {
137        Body {
138            line,
139            form,
140            weighted,
141            written: false,
142            sum: 0.0,
143        }
144    }
145
146    #[inline]
147    pub fn term(&mut self, exponent: usize, coefficient: f64) {
148        match self.form {
149            Line::Terms => {
150                if self.written {
151                    self.line.push(b',');
152                }
153                self.written = true;
154                if self.weighted {
155                    push_f64(self.line, coefficient);
156                } else {
157                    // Always exactly 1 here, and an integer is what `push_f64`
158                    // would print for it anyway -- this just does not pay the
159                    // formatter for it.
160                    push_int(self.line, coefficient as usize);
161                }
162                self.line.push(b':');
163                push_int(self.line, exponent);
164            }
165            Line::Sum => self.sum += exponent as f64 * coefficient,
166        }
167    }
168
169    /// Close the line, newline and all.
170    pub fn finish(self) {
171        if self.form == Line::Sum {
172            push_f64(self.line, self.sum);
173        }
174        self.line.push(b'\n');
175    }
176}

178/// A color copied out of the store, which is everything a line needs and
179/// nothing the store owns.
180///
181/// The two arrays are kept apart rather than interleaved into pairs for the
182/// unweighted backends' sake: they have no coefficients worth carrying — every
183/// one of them is the integer 1 — so `weights` stays empty and the copy is four
184/// bytes a term rather than sixteen.
185pub struct Snapshot {
186    tx_id: usize,
187    /// Exponents in the order [`crate::store::ColorStore::for_each_term`]
188    /// yields them, which is the order they print in.
189    blocks: Vec<usize>,
190    /// Coefficients at the same indices, or empty under an unweighted backend.
191    weights: Vec<f64>,
192}
193
194impl Snapshot {
195    fn new() -> Self {
196        Snapshot {
197            tx_id: 0,
198            blocks: Vec::new(),
199            weights: Vec::new(),
200        }
201    }
202
203    /// A term of an unweighted color, whose coefficient is 1 and is not stored.
204    #[inline]
205    pub fn push_flat(&mut self, exponent: usize) {
206        self.blocks.push(exponent);
207    }
208
209    #[inline]
210    pub fn push_weighted(&mut self, exponent: usize, coefficient: f64) {
211        self.blocks.push(exponent);
212        self.weights.push(coefficient);
213    }
214
215    fn reset(&mut self, tx_id: usize) {
216        self.tx_id = tx_id;
217        self.blocks.clear();
218        self.weights.clear();
219    }
220
221    /// Whether this snapshot carries coefficients, which is a fact about the
222    /// snapshot rather than about the pool.
223    ///
224    /// Asking the snapshot rather than being told is what makes the mismatch
225    /// unrepresentable.  The pool used to be handed a `weighted` flag of its
226    /// own, settled way back in `plan` from the backend; the two agreed by
227    /// construction, and nothing checked.  Had they ever disagreed, a flat
228    /// snapshot reaching a weighted pool would have indexed an empty `weights`
229    /// and panicked in a formatter thread -- which is the one failure this
230    /// design cannot report well.  Now there is nothing to disagree with.
231    fn weighted(&self) -> bool {
232        !self.weights.is_empty()
233    }
234
235    /// This color's line, onto the end of `line` -- a batch's lines share one
236    /// buffer, so the writer makes one `write_all` of the lot.
237    fn append(&self, line: &mut Vec<u8>, form: Line) {
238        push_int(line, self.tx_id);
239        line.push(b'\t');
240        let weighted = self.weighted();
241        let mut body = Body::new(line, form, weighted);
242        for k in 0..self.blocks.len() {
243            // A color with no terms at all prints none either way, so the two
244            // shapes cannot be told apart there and do not need to be.
245            let coefficient = if weighted { self.weights[k] } else { 1.0 };
246            body.term(self.blocks[k], coefficient);
247        }
248        body.finish();
249    }
250}

252/// A batch's lines and the snapshots they were formatted from, travelling
253/// together so that both can be handed back and filled again.
254type Done = (Vec<u8>, Vec<Snapshot>);
255
256/// A pool of formatter threads and the one writer that puts their lines in
257/// order.
258pub struct Pool {
259    /// Dispatch, one channel a worker.  Batch `b` goes to `to[b % to.len()]`,
260    /// and the writer collects from `b % to.len()`, which is what puts the
261    /// lines back in the order they were staged.
262    to: Vec<SyncSender<Vec<Snapshot>>>,
263    /// Batches the writer has finished with, for their snapshots and for the
264    /// vector that held them.
265    spare: Receiver<Vec<Snapshot>>,
266    /// The batch being filled, and how many terms are already in it.
267    batch: Vec<Snapshot>,
268    terms: usize,
269    /// Snapshots and batch vectors that have come back, to be filled again.
270    free: Vec<Snapshot>,
271    containers: Vec<Vec<Snapshot>>,
272    next: usize,
273    /// Set by the writer when a write fails, so the fold thread stops feeding a
274    /// pipeline whose far end has gone away — a closed `| head`, most often.
275    failed: Arc<AtomicBool>,
276    threads: Vec<thread::JoinHandle<()>>,
277    /// Taken by the first shutdown, so joining twice is not a panic: a write
278    /// error shuts the pool down from `dispatch`, and `finish` still runs.
279    writer: Option<thread::JoinHandle<io::Result<()>>>,
280}
281
282impl Pool {
283    /// `threads` formatter threads over `sink`, buffered a megabyte at a time
284    /// the way the serial path buffers it.
285    pub fn new(sink: Box<dyn Write + Send>, form: Line, threads: usize) -> Pool {
286        let threads = threads.max(1);
287        let failed = Arc::new(AtomicBool::new(false));
288        // The writer keeps one receiver a worker and reads them round-robin,
289        // which is what puts the lines back in dispatch order.
290        let mut collect = Vec::with_capacity(threads);
291        let mut recycle = Vec::with_capacity(threads);
292        let mut to = Vec::with_capacity(threads);
293        let mut handles = Vec::with_capacity(threads);
294
295        for _ in 0..threads {
296            let (send_work, work) = sync_channel::<Vec<Snapshot>>(DEPTH);
297            let (send_done, done) = sync_channel::<Done>(DEPTH);
298            let (send_spare_line, spare_line) = sync_channel::<Vec<u8>>(DEPTH);
299            to.push(send_work);
300            collect.push(done);
301            recycle.push(send_spare_line);
302            handles.push(thread::spawn(move || {
303                for batch in work {
304                    // A buffer the writer has finished with, or a fresh one:
305                    // `try_recv` rather than `recv` because a worker must never
306                    // wait on recycling, only benefit from it.
307                    let mut lines = spare_line.try_recv().unwrap_or_default();
308                    lines.clear();
309                    for snapshot in &batch {
310                        snapshot.append(&mut lines, form);
311                    }
312                    if send_done.send((lines, batch)).is_err() {
313                        break;
314                    }
315                }
316            }));
317        }
318
319        let (send_spare, spare) = sync_channel::<Vec<Snapshot>>(threads * DEPTH + 1);
320        let flag = Arc::clone(&failed);
321        let writer = thread::spawn(move || {
322            let mut out = io::BufWriter::with_capacity(1 << 20, sink);
323            let mut result = Ok(());
324            let mut k = 0usize;
325            // Stops at the first worker whose channel is both empty and closed.
326            // Dispatch was round-robin, so that is exactly the point where the
327            // records ran out: for every earlier `k` the worker it names still
328            // owes a line.
329            while let Ok((lines, batch)) = collect[k % threads].recv() {
330                if result.is_ok() {
331                    // One call for the whole batch, which is the other thing
332                    // batching buys.
333                    if let Err(e) = out.write_all(&lines) {
334                        // Kept, and reported from `finish`.  The loop carries on
335                        // draining: a writer that stopped receiving would block
336                        // the workers, which would block the fold thread, and
337                        // the run would hang instead of failing.
338                        result = Err(e);
339                        flag.store(true, Ordering::Release);
340                    }
341                }
342                let _ = recycle[k % threads].try_send(lines);
343                let _ = send_spare.try_send(batch);
344                k += 1;
345            }
346            result.and_then(|()| out.flush())
347        });
348
349        Pool {
350            to,
351            spare,
352            batch: Vec::with_capacity(LINES),
353            terms: 0,
354            free: Vec::new(),
355            containers: Vec::new(),
356            next: 0,
357            failed,
358            threads: handles,
359            writer: Some(writer),
360        }
361    }
362
363    /// A snapshot to fill for `tx_id`: one that has come back from the writer
364    /// if there is one, a fresh one otherwise.
365    ///
366    /// Recycling is what keeps a run of thousand-term colors from allocating a
367    /// pair of vectors per record; once the pipeline is full it comes back
368    /// every time.
369    pub fn stage(&mut self, tx_id: usize) -> Snapshot {
370        if self.free.is_empty() {
371            self.reclaim();
372        }
373        let mut snapshot = self.free.pop().unwrap_or_else(Snapshot::new);
374        snapshot.reset(tx_id);
375        snapshot
376    }
377
378    /// Take back whatever the writer has finished with, without waiting for it.
379    fn reclaim(&mut self) {
380        while let Ok(mut batch) = self.spare.try_recv() {
381            self.free.append(&mut batch);
382            self.containers.push(batch);
383        }
384    }
385
386    /// Add a filled snapshot to the batch, and send the batch once it is full.
387    ///
388    /// Full is whichever of [`LINES`] and [`TERMS`] it reaches first — see
389    /// those for why one bound is not enough.
390    pub fn dispatch(&mut self, snapshot: Snapshot) -> io::Result<()> {
391        self.terms += snapshot.blocks.len();
392        self.batch.push(snapshot);
393        if self.batch.len() >= LINES || self.terms >= TERMS {
394            return self.send();
395        }
396        Ok(())
397    }
398
399    /// Hand the batch being filled to the next worker, in turn.
400    fn send(&mut self) -> io::Result<()> {
401        if self.batch.is_empty() {
402            return Ok(());
403        }
404        if self.failed.load(Ordering::Acquire) {
405            // The far end has gone; stop here and report what it said rather
406            // than filling a pipeline nobody is reading.
407            return self.shutdown().and(Err(io::Error::other(
408                "the output failed and the reason was lost",
409            )));
410        }
411        if self.to.is_empty() {
412            // Shut down already, and not because of a write failure -- there is
413            // no path here today, and this is what keeps the `%` below from
414            // being a division by zero if one ever appears.
415            return Err(io::Error::other("the formatters have already stopped"));
416        }
417        let container = self.containers.pop().unwrap_or_else(|| Vec::with_capacity(LINES));
418        let batch = std::mem::replace(&mut self.batch, container);
419        self.terms = 0;
420        let worker = self.next;
421        self.next = (self.next + 1) % self.to.len();
422        // A worker only disconnects by panicking, since the pool owns them all
423        // and drops the senders in `shutdown`.
424        self.to[worker]
425            .send(batch)
426            .map_err(|_| io::Error::other("a formatter thread stopped"))
427    }
428
429    /// Close the dispatch channels, let the pipeline drain, and answer whatever
430    /// the writer made of it.
431    ///
432    /// Idempotent, because a write error shuts the pool down from `send` and
433    /// `finish` is still called on the way out.
434    fn shutdown(&mut self) -> io::Result<()> {
435        self.to.clear();
436        let mut panicked = false;
437        for handle in self.threads.drain(..) {
438            panicked |= handle.join().is_err();
439        }
440        let written = match self.writer.take() {
441            None => Ok(()),
442            Some(writer) => writer
443                .join()
444                .unwrap_or_else(|_| Err(io::Error::other("the writing thread panicked"))),
445        };
446        // The writer's own complaint first, since it names a cause -- a closed
447        // pipe, a full disk.
448        written?;
449        if panicked {
450            // A worker that panicked dropped its channel, and the writer stops
451            // at the first channel that is closed and empty.  So the lines
452            // behind it were never written, and the flush that followed still
453            // returned `Ok`: without this, the one path in this design that can
454            // truncate the output *and* exit 0.
455            return Err(io::Error::other(
456                "a formatter thread panicked, so the output is incomplete",
457            ));
458        }
459        Ok(())
460    }
461
462    pub fn finish(mut self) -> io::Result<()> {
463        // The last batch is almost never a full one, and it holds real lines.
464        let sent = self.send();
465        let drained = self.shutdown();
466        sent.and(drained)
467    }
468}

470/// Closing the pipeline is not something the driver can be trusted to remember.
471///
472/// [`Pool::finish`] is the ordinary way out, and `run` calls it -- but only when
473/// it reaches the end.  Every early return skips it: `?` on a malformed record,
474/// the `spends unknown transaction` error, a write failure, and a panic
475/// unwinding out of the fold.  On those paths the pool was simply dropped, and
476/// dropping a [`thread::JoinHandle`] *detaches* the thread rather than waiting
477/// for it, so the process exited with the writer still holding up to a megabyte
478/// of buffered lines and the last batch never dispatched at all.
479///
480/// Measured on a 200,000-record file with one bad record at the end: serial
481/// wrote 2,088,890 bytes and `--threads 4` wrote around 1,250,000 of them, a
482/// byte-exact prefix ending mid-line, varying run to run, with the same exit
483/// code and the same message on stderr.  On a short enough file it wrote
484/// nothing at all, the whole run having sat in the undispatched partial batch.
485/// `Output::Text` never had the problem because `BufWriter` flushes on drop.
486///
487/// So the closing goes here, where the language guarantees it runs.  `send`
488/// first, or the staged batch is still lost; both calls are idempotent, so the
489/// ordinary path through `finish` is unaffected and this does nothing.
490impl Drop for Pool {
491    fn drop(&mut self) {
492        let _ = self.send();
493        let _ = self.shutdown();
494    }
495}

502    /// A sink a test can read back afterwards.  `Send`, unlike the serial
503    /// path's, because the writing happens on a thread of the pool's own.
504    #[derive(Clone, Default)]
505    struct Shared(Arc<Mutex<Vec<u8>>>);
506
507    impl Write for Shared {
508        fn write(&mut self, buf: &[u8]) -> io::Result<usize> {
509            self.0.lock().unwrap().extend_from_slice(buf);
510            Ok(buf.len())
511        }
512        fn flush(&mut self) -> io::Result<()> {
513            Ok(())
514        }

517    /// Colors of varying length, so the workers finish out of step with each
518    /// other and the writer has real reordering to undo.
519    ///
520    /// `spread` is the longest color it will make.  It matters because the two
521    /// batch bounds close on different corpora: [`LINES`] closes a batch of
522    /// short colors and [`TERMS`] a batch of long ones, and a test that only
523    /// ever trips one of them leaves the other's arithmetic unexercised.
524    fn colors_upto(n: usize, spread: u64) -> Vec<(usize, Vec<(usize, f64)>)> {
525        let mut state = 0x9E37_79B9_7F4A_7C15u64;
526        let mut next = move || {
527            state ^= state << 13;
528            state ^= state >> 7;
529            state ^= state << 17;
530            state
531        };
532        (0..n)
533            .map(|tx| {
534                let len = (next() % spread) as usize;
535                let mut block = 0usize;
536                let terms = (0..len)
537                    .map(|_| {
538                        block += 1 + (next() % 30) as usize;
539                        (block, (next() >> 11) as f64 / (1u64 << 53) as f64)
540                    })
541                    .collect();
542                (tx, terms)
543            })
544            .collect()
545    }
546
547    fn colors(n: usize) -> Vec<(usize, Vec<(usize, f64)>)> {
548        colors_upto(n, 40)
549    }

551    /// What the serial path writes, from the same `Body` it uses.
552    fn serially(records: &[(usize, Vec<(usize, f64)>)], form: Line, weighted: bool) -> Vec<u8> {
553        let mut out = Vec::new();
554        let mut line = Vec::new();
555        for (tx, terms) in records {
556            line.clear();
557            push_int(&mut line, *tx);
558            line.push(b'\t');
559            let mut body = Body::new(&mut line, form, weighted);
560            for &(exponent, coefficient) in terms {
561                body.term(exponent, if weighted { coefficient } else { 1.0 });
562            }
563            body.finish();
564            out.extend_from_slice(&line);
565        }
566        out
567    }
568
569    fn threaded(
570        records: &[(usize, Vec<(usize, f64)>)],
571        form: Line,
572        weighted: bool,
573        threads: usize,
574    ) -> Vec<u8> {
575        let sink = Shared::default();
576        let mut pool = Pool::new(Box::new(sink.clone()), form, threads);
577        for (tx, terms) in records {
578            let mut snapshot = pool.stage(*tx);
579            for &(exponent, coefficient) in terms {
580                if weighted {
581                    snapshot.push_weighted(exponent, coefficient);
582                } else {
583                    snapshot.push_flat(exponent);
584                }
585            }
586            pool.dispatch(snapshot).expect("the sink accepts everything");
587        }
588        pool.finish().expect("the sink accepts everything");
589        let written = sink.0.lock().unwrap().clone();
590        written
591    }

593    /// The property the whole design rests on: threading changes how fast the
594    /// lines are made and nothing whatever about what they say.  Byte for byte,
595    /// at every width, because diffing one backend against another is how this
596    /// crate checks itself and a threaded run has to stay usable for it.
597    #[test]
598    fn parallel_output_is_byte_identical() {
599        // Three corpora, because the two batch bounds close on different ones.
600        // 900 short colors trip `LINES` and wrap `next` several times over;
601        // 300 long ones average ~200 terms, so `TERMS` closes a batch every
602        // forty-odd records and the partial-batch arithmetic is exercised at a
603        // different alignment; the third is neither, and is what the test used
604        // to be.
605        for &(count, spread) in &[(900usize, 6u64), (300, 400), (500, 40)] {
606        let records = colors_upto(count, spread);
607        for &weighted in &[false, true] {
608            for &form in &[Line::Terms, Line::Sum] {

610                for threads in [1usize, 2, 3, 5, 8, 16] {
611                    let got = threaded(&records, form, weighted, threads);
612                    assert_eq!(
613                        got.len(),
614                        want.len(),
615                        "weighted={} threads={} wrote {} bytes, not {}",
616                        weighted,
617                        threads,
618                        got.len(),
619                        want.len()
620                    );
621                    assert!(
622                        got == want,
623                        "weighted={} threads={} count={} spread={} wrote different bytes",
624                        weighted,
625                        threads,

635    /// The pool must close itself when it is dropped rather than finished.
636    ///
637    /// `run` calls [`Pool::finish`] only when it reaches the end of the
638    /// records; every early return -- a malformed record, a colour spending an
639    /// unknown transaction, a write error, a panic unwinding through the fold
640    /// -- drops the pool instead.  Dropping a `JoinHandle` detaches the thread,
641    /// so before [`Drop for Pool`](Pool) this lost the staged batch and up to a
642    /// megabyte of the writer's buffer: measured at 2,088,890 bytes serial
643    /// against about 1,250,000 threaded, ending mid-line and varying run to
644    /// run.  On a short enough run it wrote nothing at all, which is what this
645    /// asserts against -- 40 records fit inside one unsent batch.
646    #[test]
647    fn dropping_the_pool_writes_everything_finish_would_have() {
648        let records = colors(40);
649        let want = serially(&records, Line::Terms, true);
650        assert!(!want.is_empty(), "the corpus has to produce lines to lose");
651
652        for threads in [1usize, 4, 8] {
653            let sink = Shared::default();
654            {
655                let mut pool = Pool::new(Box::new(sink.clone()), Line::Terms, threads);
656                for (tx, terms) in &records {
657                    let mut snapshot = pool.stage(*tx);
658                    for &(exponent, coefficient) in terms {
659                        snapshot.push_weighted(exponent, coefficient);
660                    }
661                    pool.dispatch(snapshot).expect("the sink accepts everything");
662                }
663                // No `finish`: the pool goes out of scope here, which is what
664                // every early return in `run` does to it.
665            }
666            let got = sink.0.lock().unwrap().clone();
667            assert_eq!(
668                got.len(),
669                want.len(),
670                "threads={} wrote {} bytes on drop, not {}",
671                threads,
672                got.len(),
673                want.len()
674            );
675            assert!(got == want, "threads={} wrote different bytes on drop", threads);
676        }
677    }

693    /// A sink that refuses everything, which is what a closed `| head` looks
694    /// like from in here.  The run has to come back with the error rather than
695    /// hang waiting on a pipeline nobody is draining.
696    ///
697    /// The corpus is deliberately larger than the writer's one-megabyte buffer.
698    /// It used to be 2,000 short colors, about 891 KB, which never filled the
699    /// buffer -- so `Broken::write` was not called until `finish` flushed, and
700    /// the test passed through the tidy path rather than the mid-run failure it
701    /// is named for.  `wrote` is what holds it to that now.
702    #[test]
703    fn a_failing_sink_is_reported_and_does_not_hang() {
704        #[derive(Clone, Default)]
705        struct Broken(Arc<Mutex<usize>>);
706        impl Write for Broken {
707            fn write(&mut self, _: &[u8]) -> io::Result<usize> {
708                *self.0.lock().unwrap() += 1;
709                Err(io::Error::from(io::ErrorKind::BrokenPipe))
710            }
711            fn flush(&mut self) -> io::Result<()> {
712                Ok(())
713            }
714        }
715
716        let broken = Broken::default();
717        let mut pool = Pool::new(Box::new(broken.clone()), Line::Terms, 4);
718        let mut failed = None;
719        // ~4,000 colors averaging 200 terms is some tens of megabytes, so the
720        // writer reaches the sink long before the records run out.
721        for (tx, terms) in colors_upto(4_000, 400) {
722            let mut snapshot = pool.stage(tx);
723            for (exponent, coefficient) in terms {
724                snapshot.push_weighted(exponent, coefficient);
725            }
726            if let Err(e) = pool.dispatch(snapshot) {
727                failed = Some(e);
728                break;
729            }
730        }
731        let noticed_during_the_run = failed.is_some();
732        let outcome = failed.map_or_else(|| pool.finish(), Err);
733
734        assert!(outcome.is_err(), "a sink that refuses everything must fail");
735        assert!(
736            *broken.0.lock().unwrap() > 0,
737            "the sink was never written to, so nothing was actually refused"
738        );
739        assert!(
740            noticed_during_the_run,
741            "a sink failing mid-run has to stop the dispatcher, not wait for finish"
742        );
743    }

745    /// A worker that panics must not be reported as a clean run.
746    ///
747    /// It is the one shape in this design that could truncate the output *and*
748    /// exit 0: the panicking worker drops its channel, the writer stops at the
749    /// first channel that is closed and empty, and the flush that follows
750    /// succeeds.  `shutdown` joins the workers and turns a panic into an error
751    /// for exactly this reason.
752    #[test]
753    fn a_panicking_formatter_is_an_error_rather_than_a_short_run() {
754        struct Sink;
755        impl Write for Sink {
756            fn write(&mut self, buf: &[u8]) -> io::Result<usize> {
757                Ok(buf.len())
758            }
759            fn flush(&mut self) -> io::Result<()> {
760                Ok(())
761            }
762        }
763
764        // `append` indexes `weights` for every block when the snapshot carries
765        // any, so a snapshot with more blocks than weights panics in the
766        // worker.  `push_flat`/`push_weighted` cannot build one -- this reaches
767        // past them on purpose, to inject the fault.
768        let mut pool = Pool::new(Box::new(Sink), Line::Terms, 2);
769        let mut snapshot = pool.stage(1);
770        snapshot.push_weighted(7, 0.5);
771        snapshot.blocks.push(9);
772        pool.dispatch(snapshot).expect("the batch is only staged");
773
774        let outcome = pool.finish();
775        assert!(
776            outcome.is_err(),
777            "a formatter thread that panicked has to be reported, not ignored"
778        );
779    }
