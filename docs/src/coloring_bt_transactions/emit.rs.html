1//! # Formatting lines on more than one thread
2//!
3//! Turning a color into a line is the most expensive thing a text run does, and
4//! by a long way.  Measured over the first 150,000 records of
5//! `cargo run --release --example records -- --window 4000` — colors of some
6//! three thousand blocks by the end of it — with the fold and the parse held
7//! constant by comparing against `--sum`, which walks exactly the same terms
8//! and prints one number instead of all of them:
9//!
10//! ```text
11//!     --sets --fold /dev/null    2.43s      parse and fold, no lines
12//!     --sets                     4.70s      + 2.3 GB of terms
13//!     --weighted --sum           3.37s      parse and weighted fold
14//!     --weighted                50.18s      + 9.9 GB of terms
15//! ```
16//!
17//! Every number in this file names that corpus; `examples/records.rs` is what
18//! makes them checkable rather than merely stated.
19//!
20//! So formatting is 47% of an unweighted text run and 94% of a weighted one.
21//! The gap is [`crate::push_f64`]: the shortest round-tripping decimal costs
22//! about 133ns a term against 15ns for the integer path, and a weighted color
23//! spends one on every block it names.
24//!
25//! It is also the one part of the driver that is embarrassingly parallel.  A
26//! line is a pure function of `(tx_id, color)` — nothing about it looks at the
27//! store, at the records still to come, or at the line before it.
28//!
29//! ## What crosses the thread boundary
30//!
31//! A copy of the terms, not a handle on the color.
32//!
33//! Sharing the color itself is the obvious move and it is the wrong one here.
34//! It would mean `Rc` becoming `Arc` in both set backends, atomics on a
35//! refcount the fold thread touches several times a record, and — the real
36//! cost — an ownership question the stores currently answer exactly:
37//! [`crate::store::ColorStore::release`] decides whether an allocation is gone
38//! by asking whether it holds the last handle, and that question has no
39//! race-free answer once a second thread can hold one too.
40//!
41//! Copying sidesteps all of it.  A term is 12 bytes and a formatted term is
42//! about 22, so the copy is a memcpy against a decimal conversion: roughly 1ns
43//! a term against 133.  The stores keep their `Rc`, keep their layouts, and do
44//! not learn that threads exist; [`crate::poly`]'s arena, which could not have
45//! been shared at all, gets the same speedup as the others.
46//!
47//! ## Order, and why it costs nothing
48//!
49//! Record `i` goes to worker `i % threads` and the writer collects from worker
50//! `i % threads`, so the lines are written in the order they were dispatched
51//! without a sequence number, a reorder buffer, or a sort.  The output is
52//! byte-identical to the serial path — which matters beyond tidiness, since
53//! diffing `--rings` against `--sets` is how this crate checks one backend
54//! against the other, and a threaded run has to stay usable for that.
55//! `parallel_output_is_byte_identical` at the bottom of this file is the test.
56//!
57//! ## Closing it is not optional
58//!
59//! [`Pool::finish`] drains the pipeline and reports what the writer made of it,
60//! and `run` calls it — but only on the path that reaches the end of the
61//! records.  Every early return skips it, and a detached writer thread takes
62//! its buffer to the grave with it.  So the closing is in [`Drop`] as well,
63//! where the language runs it; `finish` is then the way to get at the *error*,
64//! not the way to make the output happen.  See the `impl Drop` below for what
65//! this used to cost.
66//!
67//! ## What bounds the memory
68//!
69//! Every channel into the pipeline is bounded, so a fold thread that outruns
70//! the formatters blocks instead of queueing.  The two channels *backwards* —
71//! the ones that hand a line buffer back to the worker that filled it and a
72//! snapshot back to the fold thread — are best-effort `try_send`: dropping a
73//! recycled buffer costs an allocation, where blocking on one would close a
74//! cycle in the wait graph and deadlock.  Nothing waits on recycling.
75

85/// How many batches may be in flight per worker.
86///
87/// Deep enough that a worker delayed on one long color does not stall the
88/// dispatcher, shallow enough that the pipeline holds a bounded and small
89/// multiple of a batch rather than an unbounded backlog of them.
90const DEPTH: usize = 4;
91
92/// Records a batch carries, and terms it carries, whichever it reaches first.
93///
94/// A batch rather than a record at a time because the channel costs the same
95/// whatever it carries, and what it carries varies by four orders of magnitude:
96/// a color of one block is a ten-byte line, and one of three thousand is fifty
97/// kilobytes.  Dispatching per record made a threaded run *slower than serial*
98/// on records whose colors stay small -- a microsecond of channel to hand over
99/// a line worth a hundred nanoseconds of work.
100///
101/// Over `--example records -- --window 0`, a million records whose every color
102/// is one block, where serial is 0.58s:
103///
104/// ```text
105///                     per record   batched
106///     --threads 1          1.59s     0.43s
107///     --threads 2          0.89s     0.43s
108///     --threads 4          1.19s     0.43s
109///     --threads 8          1.36s     0.43s
110/// ```
111///
112/// So both bounds, and neither alone.  [`LINES`] is what batches the small
113/// colors, where the record count is the cost; [`TERMS`] is what stops a batch
114/// of large ones from holding megabytes of formatted output per worker, where
115/// the byte count is.  A color of three thousand blocks fills a batch on its
116/// own, which is the right answer -- there the channel was never the problem.
117const LINES: usize = 256;
118const TERMS: usize = 8192;

120/// What follows the transaction id and the tab on a line.
121///
122/// One definition of it, driven either straight off the store on the fold
123/// thread or off a [`Snapshot`] on a worker, so the serial and threaded paths
124/// cannot drift into writing different bytes.
125pub struct Body<'a> {
126    line: &'a mut Vec<u8>,
127    form: Line,
128    weighted: bool,
129    /// Whether a term has been written, which is what puts the comma *between*
130    /// terms rather than after each of them.  `for_each_term` does not say
131    /// which term is last, so it is this rather than a truncation at the end.
132    written: bool,
133    /// The four running sums both of the collapsed forms are built from, in one
134    /// pass over the terms and no memory at all:
135    /// `sum w`, `sum w.b`, `sum w.b^2`, `sum w^2`.
136    ///
137    /// [`Line::Sum`] prints the second on its own; [`Line::Moments`] turns all
138    /// four into a mean, a spread and an effective count.  Kept here rather
139    /// than in the driver's loop so the serial and threaded paths accumulate
140    /// them the same way, as they format the terms the same way.
141    mass: f64,
142    first: f64,
143    second: f64,
144    squares: f64,
145    /// Set when the store handed over the first two moments outright, so
146    /// `term` must not add to them a second time.
147    exact: bool,
148    /// `sum w . exp(-s . b / L)` at each `s` of [`crate::bands::LAPLACE`],
149    /// which is all [`Line::Laplace`] prints.  Summed here off an exact
150    /// colour's terms, or handed over whole by a store that carries them, in
151    /// which case the terms are not walked at all -- the way a handed-over
152    /// [`Line::Sum`] is not.
153    laplace: [f64; 7],
154    /// Where an exponent sits on the block axis, as
155    /// [`crate::store::ColorStore::placement`] gives it: the identity for the
156    /// stores whose exponents are block ids, and the band geometry for the one
157    /// whose exponents are bands.  Only the collapsed forms read it.
158    scale: f64,
159    offset: f64,
160    /// Whether a coefficient is an `f32` riding in an `f64`, and prints as one
161    /// -- [`crate::store::ColorStore::NARROW`].
162    narrow: bool,
163}

165impl<'a> Body<'a> {
166    pub fn new(line: &'a mut Vec<u8>, form: Line, weighted: bool) -> Self {
167        Body {
168            line,
169            form,
170            weighted,
171            written: false,
172            mass: 0.0,
173            first: 0.0,
174            second: 0.0,
175            squares: 0.0,
176            exact: false,
177            laplace: [0.0; 7],
178            scale: 1.0,
179            offset: 0.0,
180            narrow: false,
181        }
182    }

184    /// The same body, reading exponents through `(scale, offset)`.
185    pub fn placed(mut self, placement: (f64, f64)) -> Self {
186        self.scale = placement.0;
187        self.offset = placement.1;
188        self
189    }
190
191    /// Take the first two moments from the store instead of summing them off
192    /// the terms, and say so.
193    ///
194    /// For a store whose terms are blocks the two agree, so nothing calls this.
195    /// For [`crate::bands`] they do not: summing its terms gives the *centre of
196    /// a band* where the block was wanted, out by up to half a band, and these
197    /// are exact.  The terms are then not walked at all for [`Line::Moments`],
198    /// which is also why a binned moments run is faster than a binned terms one.
199    pub fn from_exact_moments(mut self, moments: [f64; 3]) -> Self {
200        self.mass = moments[0];
201        self.first = moments[1];
202        self.second = moments[2];
203        self.exact = true;
204        self
205    }
206
207    /// Take the seven [`Line::Laplace`] values from the store instead of
208    /// summing them off the terms.  The same hand-over as
209    /// [`Body::from_exact_moments`], for the same reason: a band store's terms
210    /// are bands, and the sum off them would put each block at its band's
211    /// centre.  The caller does not walk the terms after this, so `term` has
212    /// nothing to skip.
213    pub fn from_exact_laplace(mut self, values: [f64; 7]) -> Self {
214        self.laplace = values;
215        self
216    }
217
218
219    /// The same body, printing coefficients as the `f32`s they are.
220    pub fn narrow(mut self, narrow: bool) -> Self {
221        self.narrow = narrow;
222        self
223    }

225    #[inline]
226    pub fn term(&mut self, exponent: usize, coefficient: f64) {
227        match self.form {
228            Line::Terms => {
229                if self.written {
230                    self.line.push(b',');
231                }
232                self.written = true;
233                if self.narrow {
234                    push_f32(self.line, coefficient as f32);
235                } else if self.weighted {
236                    push_f64(self.line, coefficient);
237                } else {
238                    // Always exactly 1 here, and an integer is what `push_f64`
239                    // would print for it anyway -- this just does not pay the
240                    // formatter for it.
241                    push_int(self.line, coefficient as usize);
242                }
243                self.line.push(b':');
244                push_int(self.line, exponent);
245            }
246            // `--sum` reads one of the four running sums, so it gets its own
247            // arm: `form` is a value and not a type, so the compiler keeps
248            // every chain it can reach, and at depth in the 2022 chain summing
249            // the other three over a colour of tens of thousands of terms was a
250            // tenth of the fold.  The product is formed exactly as the arm below
251            // forms it -- same terms, same order -- so the two agree bit for bit
252            // on the mean.
253            Line::Sum => {
254                self.first += (exponent as f64 * self.scale + self.offset) * coefficient;
255            }
256            Line::Moments => {
257                // `squares` is quadratic and no store can carry it, so it is
258                // summed here whatever else was handed over; the three linear
259                // sums are skipped when a store handed them over exactly.
260                self.squares += coefficient * coefficient;
261                if !self.exact {
262                    let block = exponent as f64 * self.scale + self.offset;
263                    self.mass += coefficient;
264                    self.first += block * coefficient;
265                    self.second += block * block * coefficient;
266                }
267            }
268            // Seven values a term, each `exp(-s . b / L)` of the term's block.
269            // Looked up rather than computed when the exponent is a block --
270            // seven `exp`s a term made this form ten times the cost of
271            // `--moments`; see `bands::laplace_table` -- and computed through
272            // `laplace_at` otherwise.  The table holds `laplace_at`'s own
273            // values, which is also what the band store seeds a coinbase with,
274            // so a colour that is one block prints the same bits from any of
275            // them.
276            Line::Laplace => {
277                let at = if self.scale == 1.0 && self.offset == 0.0 {
278                    laplace_of(exponent)
279                } else {
280                    laplace_at(exponent as f64 * self.scale + self.offset)
281                };
282                for (sum, value) in self.laplace.iter_mut().zip(at) {
283                    *sum += coefficient * value;
284                }
285            }
286        }
287    }
288
289    /// The mean block id, the spread about it, and the effective number of
290    /// blocks -- what [`Line::Moments`] prints, from the running sums.
291    ///
292    /// A colour with no terms answers three zeroes rather than three NaNs: it
293    /// is what [`Line::Sum`] already prints for one, and a NaN in a column is
294    /// worse than a zero for every reader of it.
295    fn moments(&self) -> (f64, f64, f64) {
296        if self.mass <= 0.0 {
297            return (0.0, 0.0, 0.0);
298        }
299        let mean = self.first / self.mass;
300        // `E[b^2] - E[b]^2` rather than a second pass, which a streaming line
301        // cannot make.  The cancellation is real but bounded: block ids reach
302        // some hundreds of thousands, so `mean^2` is around 1e11 and an `f64`
303        // still resolves a variance of 1e-4 -- a spread of a hundredth of a
304        // block, far below anything this number is read at.  What it can do is
305        // come out a hair below zero for a colour that sits on one block, and
306        // that is what the clamp is for; a negative under the root would be a
307        // NaN on the line.
308        let variance = (self.second / self.mass - mean * mean).max(0.0);
309        // The participation ratio, which is `1 / sum w^2` for weights that sum
310        // to one: two blocks at half each answers 2, a thousand blocks at a
311        // thousandth each answers 1000, and a colour that is nearly all one
312        // block answers nearly 1 however many blocks trail behind it.  That is
313        // the sense in which it counts blocks that *matter*, where the support
314        // size counts blocks that merely appear.
315        let effective = self.mass * self.mass / self.squares;
316        (mean, variance.sqrt(), effective)
317    }
318
319    /// Close the line, newline and all.
320    pub fn finish(self) {
321        match self.form {
322            Line::Terms => {}
323            Line::Sum => push_f64(self.line, self.first),
324            Line::Moments => {
325                let (mean, spread, effective) = self.moments();
326                push_f64(self.line, mean);
327                self.line.push(b'\t');
328                push_f64(self.line, spread);
329                self.line.push(b'\t');
330                push_f64(self.line, effective);
331            }
332            Line::Laplace => {
333                for (k, value) in self.laplace.iter().enumerate() {
334                    if k > 0 {
335                        self.line.push(b'\t');
336                    }
337                    push_f64(self.line, *value);
338                }
339            }
340        }
341        self.line.push(b'\n');
342    }
343}

345/// A color copied out of the store, which is everything a line needs and
346/// nothing the store owns.
347///
348/// The two arrays are kept apart rather than interleaved into pairs for the
349/// unweighted backends' sake: they have no coefficients worth carrying — every
350/// one of them is the integer 1 — so `weights` stays empty and the copy is four
351/// bytes a term rather than sixteen.
352pub struct Snapshot {
353    tx_id: usize,
354    /// Exponents in the order [`crate::store::ColorStore::for_each_term`]
355    /// yields them, which is the order they print in.
356    blocks: Vec<usize>,
357    /// Coefficients at the same indices, or empty under an unweighted backend.
358    weights: Vec<f64>,
359}
360
361impl Snapshot {
362    fn new() -> Self {
363        Snapshot {
364            tx_id: 0,
365            blocks: Vec::new(),
366            weights: Vec::new(),
367        }
368    }
369
370    /// A term of an unweighted color, whose coefficient is 1 and is not stored.
371    #[inline]
372    pub fn push_flat(&mut self, exponent: usize) {
373        self.blocks.push(exponent);
374    }
375
376    #[inline]
377    pub fn push_weighted(&mut self, exponent: usize, coefficient: f64) {
378        self.blocks.push(exponent);
379        self.weights.push(coefficient);
380    }
381
382    fn reset(&mut self, tx_id: usize) {
383        self.tx_id = tx_id;
384        self.blocks.clear();
385        self.weights.clear();
386    }
387
388    /// Whether this snapshot carries coefficients, which is a fact about the
389    /// snapshot rather than about the pool.
390    ///
391    /// Asking the snapshot rather than being told is what makes the mismatch
392    /// unrepresentable.  The pool used to be handed a `weighted` flag of its
393    /// own, settled way back in `plan` from the backend; the two agreed by
394    /// construction, and nothing checked.  Had they ever disagreed, a flat
395    /// snapshot reaching a weighted pool would have indexed an empty `weights`
396    /// and panicked in a formatter thread -- which is the one failure this
397    /// design cannot report well.  Now there is nothing to disagree with.
398    fn weighted(&self) -> bool {
399        !self.weights.is_empty()
400    }
401
402    /// This color's line, onto the end of `line` -- a batch's lines share one
403    /// buffer, so the writer makes one `write_all` of the lot.
404    fn append(&self, line: &mut Vec<u8>, form: Line, narrow: bool) {
405        push_int(line, self.tx_id);
406        line.push(b'\t');
407        let weighted = self.weighted();
408        let mut body = Body::new(line, form, weighted).narrow(narrow);
409        for k in 0..self.blocks.len() {
410            // A color with no terms at all prints none either way, so the two
411            // shapes cannot be told apart there and do not need to be.
412            let coefficient = if weighted { self.weights[k] } else { 1.0 };
413            body.term(self.blocks[k], coefficient);
414        }
415        body.finish();
416    }
417}

419/// A batch's lines and the snapshots they were formatted from, travelling
420/// together so that both can be handed back and filled again.
421type Done = (Vec<u8>, Vec<Snapshot>);
422
423/// A pool of formatter threads and the one writer that puts their lines in
424/// order.
425pub struct Pool {
426    /// Dispatch, one channel a worker.  Batch `b` goes to `to[b % to.len()]`,
427    /// and the writer collects from `b % to.len()`, which is what puts the
428    /// lines back in the order they were staged.
429    to: Vec<SyncSender<Vec<Snapshot>>>,
430    /// Batches the writer has finished with, for their snapshots and for the
431    /// vector that held them.
432    spare: Receiver<Vec<Snapshot>>,
433    /// The batch being filled, and how many terms are already in it.
434    batch: Vec<Snapshot>,
435    terms: usize,
436    /// Snapshots and batch vectors that have come back, to be filled again.
437    free: Vec<Snapshot>,
438    containers: Vec<Vec<Snapshot>>,
439    next: usize,
440    /// Set by the writer when a write fails, so the fold thread stops feeding a
441    /// pipeline whose far end has gone away — a closed `| head`, most often.
442    failed: Arc<AtomicBool>,
443    threads: Vec<thread::JoinHandle<()>>,
444    /// Taken by the first shutdown, so joining twice is not a panic: a write
445    /// error shuts the pool down from `dispatch`, and `finish` still runs.
446    writer: Option<thread::JoinHandle<io::Result<()>>>,
447}
448
449impl Pool {
450    /// `threads` formatter threads over `sink`, buffered a megabyte at a time
451    /// the way the serial path buffers it.  The driver goes through
452    /// [`Pool::with_lanes`], since it knows the store; this is the tests'.
453    #[cfg(test)]
454    pub fn new(sink: Box<dyn Write + Send>, form: Line, threads: usize) -> Pool {
455        Pool::with_lanes(sink, form, threads, false)
456    }
457
458    /// `threads` formatter threads over `sink`, buffered a megabyte at a time
459    /// the way the serial path buffers it, with the coefficients printed as
460    /// `f32`s when `narrow` -- [`crate::store::ColorStore::NARROW`], which the
461    /// pool has to be told because it formats a copy of the colour and never
462    /// sees the store.
463    pub fn with_lanes(
464        sink: Box<dyn Write + Send>,
465        form: Line,
466        threads: usize,
467        narrow: bool,
468    ) -> Pool {
469        let threads = threads.max(1);
470        let failed = Arc::new(AtomicBool::new(false));
471        // The writer keeps one receiver a worker and reads them round-robin,
472        // which is what puts the lines back in dispatch order.
473        let mut collect = Vec::with_capacity(threads);
474        let mut recycle = Vec::with_capacity(threads);
475        let mut to = Vec::with_capacity(threads);
476        let mut handles = Vec::with_capacity(threads);
477
478        for _ in 0..threads {
479            let (send_work, work) = sync_channel::<Vec<Snapshot>>(DEPTH);
480            let (send_done, done) = sync_channel::<Done>(DEPTH);
481            let (send_spare_line, spare_line) = sync_channel::<Vec<u8>>(DEPTH);
482            to.push(send_work);
483            collect.push(done);
484            recycle.push(send_spare_line);
485            handles.push(thread::spawn(move || {
486                for batch in work {
487                    // A buffer the writer has finished with, or a fresh one:
488                    // `try_recv` rather than `recv` because a worker must never
489                    // wait on recycling, only benefit from it.
490                    let mut lines = spare_line.try_recv().unwrap_or_default();
491                    lines.clear();
492                    for snapshot in &batch {
493                        snapshot.append(&mut lines, form, narrow);
494                    }
495                    if send_done.send((lines, batch)).is_err() {
496                        break;
497                    }
498                }
499            }));
500        }
501
502        let (send_spare, spare) = sync_channel::<Vec<Snapshot>>(threads * DEPTH + 1);
503        let flag = Arc::clone(&failed);
504        let writer = thread::spawn(move || {
505            let mut out = io::BufWriter::with_capacity(1 << 20, sink);
506            let mut result = Ok(());
507            let mut k = 0usize;
508            // Stops at the first worker whose channel is both empty and closed.
509            // Dispatch was round-robin, so that is exactly the point where the
510            // records ran out: for every earlier `k` the worker it names still
511            // owes a line.
512            while let Ok((lines, batch)) = collect[k % threads].recv() {
513                if result.is_ok() {
514                    // One call for the whole batch, which is the other thing
515                    // batching buys.
516                    if let Err(e) = out.write_all(&lines) {
517                        // Kept, and reported from `finish`.  The loop carries on
518                        // draining: a writer that stopped receiving would block
519                        // the workers, which would block the fold thread, and
520                        // the run would hang instead of failing.
521                        result = Err(e);
522                        flag.store(true, Ordering::Release);
523                    }
524                }
525                let _ = recycle[k % threads].try_send(lines);
526                let _ = send_spare.try_send(batch);
527                k += 1;
528            }
529            result.and_then(|()| out.flush())
530        });
531
532        Pool {
533            to,
534            spare,
535            batch: Vec::with_capacity(LINES),
536            terms: 0,
537            free: Vec::new(),
538            containers: Vec::new(),
539            next: 0,
540            failed,
541            threads: handles,
542            writer: Some(writer),
543        }
544    }
545
546    /// A snapshot to fill for `tx_id`: one that has come back from the writer
547    /// if there is one, a fresh one otherwise.
548    ///
549    /// Recycling is what keeps a run of thousand-term colors from allocating a
550    /// pair of vectors per record; once the pipeline is full it comes back
551    /// every time.
552    pub fn stage(&mut self, tx_id: usize) -> Snapshot {
553        if self.free.is_empty() {
554            self.reclaim();
555        }
556        let mut snapshot = self.free.pop().unwrap_or_else(Snapshot::new);
557        snapshot.reset(tx_id);
558        snapshot
559    }
560
561    /// Take back whatever the writer has finished with, without waiting for it.
562    fn reclaim(&mut self) {
563        while let Ok(mut batch) = self.spare.try_recv() {
564            self.free.append(&mut batch);
565            self.containers.push(batch);
566        }
567    }
568
569    /// Add a filled snapshot to the batch, and send the batch once it is full.
570    ///
571    /// Full is whichever of [`LINES`] and [`TERMS`] it reaches first — see
572    /// those for why one bound is not enough.
573    pub fn dispatch(&mut self, snapshot: Snapshot) -> io::Result<()> {
574        self.terms += snapshot.blocks.len();
575        self.batch.push(snapshot);
576        if self.batch.len() >= LINES || self.terms >= TERMS {
577            return self.send();
578        }
579        Ok(())
580    }
581
582    /// Hand the batch being filled to the next worker, in turn.
583    fn send(&mut self) -> io::Result<()> {
584        if self.batch.is_empty() {
585            return Ok(());
586        }
587        if self.failed.load(Ordering::Acquire) {
588            // The far end has gone; stop here and report what it said rather
589            // than filling a pipeline nobody is reading.
590            return self.shutdown().and(Err(io::Error::other(
591                "the output failed and the reason was lost",
592            )));
593        }
594        if self.to.is_empty() {
595            // Shut down already, and not because of a write failure -- there is
596            // no path here today, and this is what keeps the `%` below from
597            // being a division by zero if one ever appears.
598            return Err(io::Error::other("the formatters have already stopped"));
599        }
600        let container = self.containers.pop().unwrap_or_else(|| Vec::with_capacity(LINES));
601        let batch = std::mem::replace(&mut self.batch, container);
602        self.terms = 0;
603        let worker = self.next;
604        self.next = (self.next + 1) % self.to.len();
605        // A worker only disconnects by panicking, since the pool owns them all
606        // and drops the senders in `shutdown`.
607        self.to[worker]
608            .send(batch)
609            .map_err(|_| io::Error::other("a formatter thread stopped"))
610    }
611
612    /// Close the dispatch channels, let the pipeline drain, and answer whatever
613    /// the writer made of it.
614    ///
615    /// Idempotent, because a write error shuts the pool down from `send` and
616    /// `finish` is still called on the way out.
617    fn shutdown(&mut self) -> io::Result<()> {
618        self.to.clear();
619        let mut panicked = false;
620        for handle in self.threads.drain(..) {
621            panicked |= handle.join().is_err();
622        }
623        let written = match self.writer.take() {
624            None => Ok(()),
625            Some(writer) => writer
626                .join()
627                .unwrap_or_else(|_| Err(io::Error::other("the writing thread panicked"))),
628        };
629        // The writer's own complaint first, since it names a cause -- a closed
630        // pipe, a full disk.
631        written?;
632        if panicked {
633            // A worker that panicked dropped its channel, and the writer stops
634            // at the first channel that is closed and empty.  So the lines
635            // behind it were never written, and the flush that followed still
636            // returned `Ok`: without this, the one path in this design that can
637            // truncate the output *and* exit 0.
638            return Err(io::Error::other(
639                "a formatter thread panicked, so the output is incomplete",
640            ));
641        }
642        Ok(())
643    }
644
645    pub fn finish(mut self) -> io::Result<()> {
646        // The last batch is almost never a full one, and it holds real lines.
647        let sent = self.send();
648        let drained = self.shutdown();
649        sent.and(drained)
650    }
651}
652
653/// Closing the pipeline is not something the driver can be trusted to remember.
654///
655/// [`Pool::finish`] is the ordinary way out, and `run` calls it -- but only when
656/// it reaches the end.  Every early return skips it: `?` on a malformed record,
657/// the `spends unknown transaction` error, a write failure, and a panic
658/// unwinding out of the fold.  On those paths the pool was simply dropped, and
659/// dropping a [`thread::JoinHandle`] *detaches* the thread rather than waiting
660/// for it, so the process exited with the writer still holding up to a megabyte
661/// of buffered lines and the last batch never dispatched at all.
662///
663/// Measured on a 200,000-record file with one bad record at the end: serial
664/// wrote 2,088,890 bytes and `--threads 4` wrote around 1,250,000 of them, a
665/// byte-exact prefix ending mid-line, varying run to run, with the same exit
666/// code and the same message on stderr.  On a short enough file it wrote
667/// nothing at all, the whole run having sat in the undispatched partial batch.
668/// `Output::Text` never had the problem because `BufWriter` flushes on drop.
669///
670/// So the closing goes here, where the language guarantees it runs.  `send`
671/// first, or the staged batch is still lost; both calls are idempotent, so the
672/// ordinary path through `finish` is unaffected and this does nothing.
673impl Drop for Pool {
674    fn drop(&mut self) {
675        let _ = self.send();
676        let _ = self.shutdown();
677    }
678}

691        fn write(&mut self, buf: &[u8]) -> io::Result<usize> {
692            self.0.lock().unwrap().extend_from_slice(buf);
693            Ok(buf.len())
694        }

700    /// Colors of varying length, so the workers finish out of step with each
701    /// other and the writer has real reordering to undo.
702    ///
703    /// `spread` is the longest color it will make.  It matters because the two
704    /// batch bounds close on different corpora: [`LINES`] closes a batch of
705    /// short colors and [`TERMS`] a batch of long ones, and a test that only
706    /// ever trips one of them leaves the other's arithmetic unexercised.
707    fn colors_upto(n: usize, spread: u64) -> Vec<(usize, Vec<(usize, f64)>)> {
708        let mut state = 0x9E37_79B9_7F4A_7C15u64;
709        let mut next = move || {
710            state ^= state << 13;
711            state ^= state >> 7;
712            state ^= state << 17;
713            state
714        };
715        (0..n)
716            .map(|tx| {
717                let len = (next() % spread) as usize;
718                let mut block = 0usize;
719                let terms = (0..len)
720                    .map(|_| {
721                        block += 1 + (next() % 30) as usize;
722                        (block, (next() >> 11) as f64 / (1u64 << 53) as f64)
723                    })
724                    .collect();
725                (tx, terms)
726            })
727            .collect()
728    }

730    fn colors(n: usize) -> Vec<(usize, Vec<(usize, f64)>)> {
731        colors_upto(n, 40)
732    }

734    /// What the serial path writes, from the same `Body` it uses.
735    fn serially(records: &[(usize, Vec<(usize, f64)>)], form: Line, weighted: bool) -> Vec<u8> {
736        let mut out = Vec::new();
737        let mut line = Vec::new();
738        for (tx, terms) in records {
739            line.clear();
740            push_int(&mut line, *tx);
741            line.push(b'\t');
742            let mut body = Body::new(&mut line, form, weighted);
743            for &(exponent, coefficient) in terms {
744                body.term(exponent, if weighted { coefficient } else { 1.0 });
745            }
746            body.finish();
747            out.extend_from_slice(&line);
748        }
749        out
750    }

752    fn threaded(
753        records: &[(usize, Vec<(usize, f64)>)],
754        form: Line,
755        weighted: bool,
756        threads: usize,
757    ) -> Vec<u8> {
758        let sink = Shared::default();
759        let mut pool = Pool::new(Box::new(sink.clone()), form, threads);
760        for (tx, terms) in records {
761            let mut snapshot = pool.stage(*tx);
762            for &(exponent, coefficient) in terms {
763                if weighted {
764                    snapshot.push_weighted(exponent, coefficient);
765                } else {
766                    snapshot.push_flat(exponent);
767                }
768            }
769            pool.dispatch(snapshot).expect("the sink accepts everything");
770        }
771        pool.finish().expect("the sink accepts everything");
772        let written = sink.0.lock().unwrap().clone();
773        written
774    }

803                    );

813            }
814        }
815        }

818    /// The pool must close itself when it is dropped rather than finished.
819    ///
820    /// `run` calls [`Pool::finish`] only when it reaches the end of the
821    /// records; every early return -- a malformed record, a colour spending an
822    /// unknown transaction, a write error, a panic unwinding through the fold
823    /// -- drops the pool instead.  Dropping a `JoinHandle` detaches the thread,
824    /// so before [`Drop for Pool`](Pool) this lost the staged batch and up to a
825    /// megabyte of the writer's buffer: measured at 2,088,890 bytes serial
826    /// against about 1,250,000 threaded, ending mid-line and varying run to
827    /// run.  On a short enough run it wrote nothing at all, which is what this
828    /// asserts against -- 40 records fit inside one unsent batch.

830    fn dropping_the_pool_writes_everything_finish_would_have() {
831        let records = colors(40);
832        let want = serially(&records, Line::Terms, true);
833        assert!(!want.is_empty(), "the corpus has to produce lines to lose");
834
835        for threads in [1usize, 4, 8] {
836            let sink = Shared::default();
837            {
838                let mut pool = Pool::new(Box::new(sink.clone()), Line::Terms, threads);
839                for (tx, terms) in &records {

841                    for &(exponent, coefficient) in terms {
842                        snapshot.push_weighted(exponent, coefficient);
843                    }
844                    pool.dispatch(snapshot).expect("the sink accepts everything");
845                }
846                // No `finish`: the pool goes out of scope here, which is what
847                // every early return in `run` does to it.
848            }
849            let got = sink.0.lock().unwrap().clone();
850            assert_eq!(
851                got.len(),
852                want.len(),
853                "threads={} wrote {} bytes on drop, not {}",
854                threads,
855                got.len(),
856                want.len()
857            );
858            assert!(got == want, "threads={} wrote different bytes on drop", threads);
859        }

876    /// A sink that refuses everything, which is what a closed `| head` looks
877    /// like from in here.  The run has to come back with the error rather than
878    /// hang waiting on a pipeline nobody is draining.
879    ///
880    /// The corpus is deliberately larger than the writer's one-megabyte buffer.
881    /// It used to be 2,000 short colors, about 891 KB, which never filled the
882    /// buffer -- so `Broken::write` was not called until `finish` flushed, and
883    /// the test passed through the tidy path rather than the mid-run failure it
884    /// is named for.  `wrote` is what holds it to that now.
885    #[test]
886    fn a_failing_sink_is_reported_and_does_not_hang() {
887        #[derive(Clone, Default)]
888        struct Broken(Arc<Mutex<usize>>);
889        impl Write for Broken {
890            fn write(&mut self, _: &[u8]) -> io::Result<usize> {
891                *self.0.lock().unwrap() += 1;
892                Err(io::Error::from(io::ErrorKind::BrokenPipe))
893            }
894            fn flush(&mut self) -> io::Result<()> {
895                Ok(())
896            }
897        }
898
899        let broken = Broken::default();
900        let mut pool = Pool::new(Box::new(broken.clone()), Line::Terms, 4);
901        let mut failed = None;
902        // ~4,000 colors averaging 200 terms is some tens of megabytes, so the
903        // writer reaches the sink long before the records run out.
904        for (tx, terms) in colors_upto(4_000, 400) {
905            let mut snapshot = pool.stage(tx);
906            for (exponent, coefficient) in terms {
907                snapshot.push_weighted(exponent, coefficient);
908            }
909            if let Err(e) = pool.dispatch(snapshot) {
910                failed = Some(e);
911                break;
912            }
913        }
914        let noticed_during_the_run = failed.is_some();
915        let outcome = failed.map_or_else(|| pool.finish(), Err);
916
917        assert!(outcome.is_err(), "a sink that refuses everything must fail");
918        assert!(
919            *broken.0.lock().unwrap() > 0,
920            "the sink was never written to, so nothing was actually refused"
921        );
922        assert!(
923            noticed_during_the_run,
924            "a sink failing mid-run has to stop the dispatcher, not wait for finish"
925        );
926    }

928    /// A worker that panics must not be reported as a clean run.
929    ///
930    /// It is the one shape in this design that could truncate the output *and*
931    /// exit 0: the panicking worker drops its channel, the writer stops at the
932    /// first channel that is closed and empty, and the flush that follows
933    /// succeeds.  `shutdown` joins the workers and turns a panic into an error
934    /// for exactly this reason.
935    #[test]
936    fn a_panicking_formatter_is_an_error_rather_than_a_short_run() {
937        struct Sink;
938        impl Write for Sink {
939            fn write(&mut self, buf: &[u8]) -> io::Result<usize> {
940                Ok(buf.len())
941            }
942            fn flush(&mut self) -> io::Result<()> {
943                Ok(())
944            }
945        }
946
947        // `append` indexes `weights` for every block when the snapshot carries
948        // any, so a snapshot with more blocks than weights panics in the
949        // worker.  `push_flat`/`push_weighted` cannot build one -- this reaches
950        // past them on purpose, to inject the fault.
951        let mut pool = Pool::new(Box::new(Sink), Line::Terms, 2);
952        let mut snapshot = pool.stage(1);
953        snapshot.push_weighted(7, 0.5);
954        snapshot.blocks.push(9);
955        pool.dispatch(snapshot).expect("the batch is only staged");
956
957        let outcome = pool.finish();
958        assert!(
959            outcome.is_err(),
960            "a formatter thread that panicked has to be reported, not ignored"
961        );
962    }
